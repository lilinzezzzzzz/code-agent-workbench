# 新建项目工作树

用户明确要求新建时才执行。按用户选择的起始 ref 创建工作树。项目、环境和任务分支名按用户指定或项目约定确定。复用当前聊天，以下流程从现有项目 checkout 开始。

1. **确定项目与基线。** 核对来源 checkout、当前分支、工作树状态和适用的仓库指令。
   - 用户已指定分支、tag 或 commit，或明确选择当前分支、项目默认分支时，解析并核对对应的 ref。分支基线的解析与远端刷新遵循[共享规则](../_shared/git-remote-base-resolution.md)。
   - 用户未选择基线时，创建前询问一次。列出可用的当前分支和项目默认分支，给出推荐项，并标明本地分支与远端跟踪分支，例如 `refs/heads/main` 和 `origin/main`。用户选择默认环境时，仍需单独确认缺失的基线。
   - 确认可用的任务分支名。项目无命名约定时使用 `codex/` 前缀。
2. **确定初始化环境。** 先查项目中 Codex 已有的本地环境配置。检查项目入口 checkout 的 `.codex/environments/`（常见配置为 `environment.toml`），因为该目录可能未纳入 Git，新工作树里可能没有。以用户指定环境、项目已选默认环境或唯一明确适用的配置为依据。若多个环境都可能是默认且无法确认，先问用户。明确要求初始化但找不到配置时，先说明缺少什么。沿用项目脚本和现有的 `.worktreeinclude`。
3. **创建并附加。**
   - 用户未要求保留原标题时，在创建前从当前聊天或明确的父聊天引用确定附加目标的 `threadId` 和 `hostId`。目标唯一时，用 `read_thread`（`includeTurns: false`）记录原 `cwd`，供识别旧标签。原 `cwd` 取不到时仍可继续创建。
   - 确认用户已选择基线且 ref 已核对后，调用 Codex 的 `create_worktree` 工具，传入已确认的项目根目录及 ref。如果工具支持环境参数，传入已确认的环境。返回挂起状态时，用 `get_worktree_creation_status` 等待同一操作完成。
   - 创建成功后使用返回的工作区路径执行命令。仅在附加失败时使用 `attach_worktree` 重试附加，避免创建第二个工作树。
4. **更新聊天标题。** 工作树附加成功后立即更新实际接收工作树的聊天。用户要求保留原标题时跳过。用 `read_thread`（`includeTurns: false`）读取目标当前标题，再按[共享标题规则](../_shared/worktree-chat-title.md)，根据工具返回的新工作区路径取标签，并根据目标聊天的工作上下文和工作内容拟定正文。无法确认目标或工作树标签、缺少拟定正文的依据，或标题读写失败时，继续后续步骤，并在交付时说明标题状态。
5. **检出任务分支。** 验证新工作树处于预期提交。确保新工作树检出任务分支。工具仅检出基线时，按仓库约定创建并检出任务分支。使用 Git 已有的权限审批机制处理受保护的元数据写入。
6. **执行环境初始化。** 先用工具结果或初始化日志确认是否已运行。若创建工具只检出了 Git 工作树，读取来源 checkout 的已选配置并检查实际脚本。用 TOML 解析器提取通用或主机平台的设置脚本，例如 macOS 的 `setup.darwin.script`。通用和平台脚本均有内容时，依据项目配置约定或实际运行证据确认执行关系。在返回的新工作区路径下，用项目指定的 shell 和上下文运行脚本。项目脚本使用 `CODEX_WORKTREE_PATH` 时，将其设为新工作区的绝对路径。安装失败时保留已创建的工作树，依据失败步骤诊断并在可安全重试时继续。
7. **核验并交付。** 确认附加成功、路径、分支、基线和工作树状态。按配置检查安装结果和预期文件。项目依赖 `.worktreeinclude` 时，检查必需文件的实际复制结果。区分创建工具执行的初始化与手动补跑。报告最终标题或标题状态，以及其他尚未完成的步骤或实际失败原因。

- 「基于 `origin/main` 新建工作树，用当前项目的默认环境初始化。」核对远端 ref 后创建。
- 「用当前项目的默认环境新建工作树。」先询问起始 ref。
